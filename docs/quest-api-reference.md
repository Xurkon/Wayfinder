# Wayfinder quest API reference

This reference distinguishes methods present in X2Quest dumps from methods the local addon API inventory allows addons to call. Presence in a runtime dump or generated reference does not grant permission to call a method.

## Methods allowed by the local X2Quest inventory

The `x2/legacy-docs/api_functions.txt` inventory explicitly places these in its **Allowed functions** section:

- `GetActiveQuestListCount()` and `GetActiveQuestType(index)` enumerate active-list entries. The count includes completed entries and is not guaranteed to match the visible journal count.
- `GetQuestContextMainTitle(questType)` reads a quest title.
- `IsCompleted(questType)` reads completion state.
- `SetTrackingActiveQuest(index)` selects a tracked quest. ChoreTracker resolves the quest ID back to its active-list index before calling it.

The same local inventory allows `X2Sound:PlayUISound(soundName, duplicable)`. The generated `SOUND_NAME` type includes `event_quest_completed_normal`; Wayfinder uses that documented name for its optional completion sound. The control is disabled by default, and playback/event timing still needs live verification.

Wayfinder's core runtime quest scan uses these locally allowed methods. It accepts only finite positive integer IDs, deduplicates active-list entries, reads titles and completion state, shows completed entries by default, and includes unreadable completion states rather than silently dropping them. Completion is not used to decide active-list membership; it only controls row presentation when the user hides completed quests. The user can filter completed entries in settings. Existing version 2 settings and profiles migrate once to the show-completed default. The same ID validation is applied to auto-tracking and completion alerts. Optional objective rows separately use the newer explicitly enabled getter documented below.

ArcheRage's April 15, 2025 [server update](https://na.archerage.to/forums/threads/server-updates-4-15-fishers-clipper-upgrade-and-other-updates.12227/) explicitly enabled `GetActiveQuestListCount()`, `GetActiveQuestType(idx)`, and `SetTrackingActiveQuest(idx)` for addons. The September 8, 2026 [server update](https://na.archerage.to/forums/threads/server-updates-9-8-auction-house-price-limit-diseased-animals-butchering-and-other-updates.13660/) later enabled `GetQuestJournalObjectiveCount(idx)` and `GetQuestJournalObjectiveText(idx, objIdx)`. The October 27, 2026 update enabled `GetActiveQuestObjectiveText(type, objIdx)`. These explicit server announcements supersede the stale local inventory for those exact signatures; they do not grant category, status, main-list, or by-type journal access.

## Present in dumps, but marked not allowed

The X2 runtime dump and generated [X2Quest reference](https://noviern.github.io/x2/reference/api/X2Quest.html) expose additional methods. The local legacy inventory places the following under **Available/not allowed functions**:

- Category and membership filters such as `IsMainQuest`, `IsHiddenQuest`, `IsTodayQuest`, `IsSagaQuest`, `IsPublicQuest`, and `GetMainQuestListCount` / `GetMainQuestType`.
- Status and category getters such as `GetActiveQuestListStatus`, `GetActiveQuestListStatusByType`, `GetTrackingActiveQuest`, `GetQuestCategoryNameByQuestType`, and related methods.
- Direct journal-state predicates `IsProgressQuestInJournal(questType)` and `IsReadyQuestInJournal(questType)`, which may be useful for identifying accepted entries from the broader active list but are not allowed by the local inventory.
- By-type journal objective methods, body getters, category labels, and other journal helpers not explicitly listed in a server permission update.

The local inventory lists `GetQuestJournalObjectiveCount`, `GetQuestJournalObjectiveText`, and `GetActiveQuestObjectiveText` as available/not allowed, but official server updates explicitly enabled the two indexed journal methods on September 8, 2026 and active-quest objective text on October 27, 2026. Wayfinder uses `GetQuestJournalObjectiveCount(index)` diagnostically for each unique active-list slot and does not filter entries from its result. Positive, zero, and failed reads are counted; the sample line includes the count. This is evidence for comparing against the native journal, not a membership guarantee: valid completed rows can have zero objectives. The optional objective renderer uses `GetActiveQuestObjectiveText(questType, objIdx)` with a 1-based index, stops on `false`, and is bounded by `MAX_QUEST_OBJECTIVE` (10). API behavior and text layout still need live verification. Other by-type journal access remains unavailable, and hidden/public/main-list filtering remains unresolved.

Official permission sources: [ArcheRage server updates 9/8, “GetQuestJournalObjectiveCount” and “GetQuestJournalObjectiveText”](https://na.archerage.to/forums/threads/server-updates-9-8-auction-house-price-limit-diseased-animals-butchering-and-other-updates.13660/) and [server updates 10/27, “GetActiveQuestObjectiveText”](https://na.archerage.to/forums/threads/server-updates-10-27-general-updates.13807/). Neither update lists the stock main-list or category-membership getters below. The stock calling pattern is in `aagamedump/scriptsbin/x2ui/questcontext/common.lua` and `quest_context_common.lua`. The installed X2 LuaLS stub still lacks `GetActiveQuestObjectiveText`, so the X2-aware Lua Language Server reports an undefined-field warning for this server-enabled function; the source retains a runtime guard.

As of October 29, 2026, a search of ArcheRage's public update posts found no later announcement enabling `GetQuestJournalTitle`, `GetQuestJournalObjectiveCountByType`, `IsProgressQuestInJournal`, `IsReadyQuestInJournal`, or the stock category/main-list methods. This is a search result, not confirmation that the server will never expose them; recheck announcements before relying on any newly available method.

Wayfinder resolves each quest ID against the current active-list order immediately before invoking `SetTrackingActiveQuest(activeListIndex)`, both for a row click and opt-in accepted-quest auto-tracking. This avoids using the scan-time index if the active list changed after the row was drawn. The call remains a request; Wayfinder cannot read the current selection through `GetTrackingActiveQuest()` under the local policy, so selected-row highlighting remains pending. Index lookup and selection behavior still need live verification.

## Native notifier tracking data

The stock client keeps ordinary notifier selections in `notifierData.questList`. The stock Lua global `GetNotifierQuestList()` returns that array, and `quest_notifier.lua` uses it to build the notifier rows. Daily assignments are separate: `GetTodayQuestList()` returns `notifierData.todayQuestList`, which the assignment notifier reads. The quest-log checkbox getter is another stock Lua global, `GetQuestListCheckValue(questType)`, returning `questContextStateValues.checkBoxStates[questType]`; the checkbox callback updates that state and adds/removes the quest from the notifier list.

These names are stock Lua helpers, not `X2Quest` methods. Their engine-backed state is read through `X2:GetQuestNotifierListUiData()` and `X2:GetQuestContextStateValuesUiData()`, both listed as **Available/not allowed** in the installed API inventory. Wayfinder's startup and manual Refresh probes check whether the helpers are visible in the addon namespace, safely call only those Lua getters, report table counts and up to eight sample values, and sample the checkbox getter when possible. They check `GetQuestAcceptZoneName` presence without invoking it. A visible stock global is not equivalent to an officially permitted addon API; live probing must confirm availability and results before the tracker changes its data source. The active-list lookup may still be needed to resolve a selected `questType` to the current index for `SetTrackingActiveQuest`.

The user's WF27 live probe showed all three stock globals missing in Wayfinder's addon namespace: `GetNotifierQuestList`, `GetTodayQuestList`, and `GetQuestListCheckValue`. It also showed `X2Quest.GetNotifierQuestList` and `X2Quest.GetQuestAcceptZoneName` as nil. The accompanying scan read 494 active-list IDs, of which 440 were reported not completed; 440 candidates matched the current eligibility/title filters and 210 rendered outside collapsed sections. Those counts do not identify which quests are selected in the native notifier. Wayfinder therefore has no verified notifier-membership source in the current addon environment, and must not present the 440 candidates as the native tracked set. The source change is blocked on a permitted notifier/tracked-list accessor or another confirmed addon-visible state source.

WF28 adds a **presence-only** runtime matrix for the alternative names suggested during debugging: `X2Quest.IsTrackedQuest`, `GetQuestContextNotify`, and `GetQuestContextState`; journal/status candidates (`IsProgressQuestInJournal`, `IsReadyQuestInJournal`, `GetActiveQuestListStatus`, `GetActiveQuestListStatusByType`, `IsCompleted`); category predicates; same-named stock globals including `IsCompleteQuest`; and the underlying `X2` UI-data getters. It does not invoke these candidates. A function showing as present would only justify a carefully controlled permission/semantics investigation; it would not prove it returns the native checked-quest set. Compare the WF28 chat output after a client restart or addon refresh. The previously observed missing stock notifier globals remain the only live result until that new output is collected.

Other apparent options are not equivalent to a notifier selection list. `GetTrackingActiveQuest()` is singular and marked not allowed locally; status and journal predicates are also restricted in the installed inventory. The local stock `ADD_NOTIFY_QUEST_INFO`, `REMOVE_NOTIFY_QUEST_INFO`, and `CLEAR_NOTIFY_QUEST_INFO` handlers update world/road-map quest notification markers, while `QUEST_NOTIFIER_START` is a notifier lifecycle event; the source does not show them exposing the complete checked quest list to third-party addons. The most reliable fix remains a server-approved getter returning the selected ordinary notifier quest types (and, separately if needed, selected daily assignments), or an approved checkbox-state accessor. A Wayfinder-owned selection list is a possible independent mode, but cannot truthfully mirror changes made in the native quest log.

## Why the 497-slot list cannot yet be made exact

This section records the earlier full-journal parity investigation. The current feature target is the selected native tracker HUD set described above, not a complete quest-journal replica.

### Quest identifiers are not quest categories

`GetActiveQuestType(index)` returns the `questType` identifier for the quest at an active-list slot. That number identifies an individual quest; it does not encode a documented category range. Main, saga, daily, weekly, livelihood/vocation, hidden, public, and normal are classifications of quest IDs, not separate numeric ID sequences that Wayfinder can safely infer. The `QUEST_MARK_ORDER_*` globals (values 1 through 7 in the local X2 definitions) are sort/order constants, not category IDs or active-list offsets. The screenshot's Race/Common/General/Daily/Weekly/Vocation counts are category totals in that UI; they do not expose a mapping from those categories to active-list slots or quest IDs.

The stock implementation demonstrates the split. `GetQuestItemsGroupedByCategory()` walks `GetActiveQuestListCount()` / `GetActiveQuestType()` and applies `AddableQuest(qtype)`, which rejects hidden, today, saga, and public quests; it places non-main quests into zone-category groups. It then separately walks `GetMainQuestListCount()` / `GetMainQuestType()` and groups main quests by chapter. `GetQuestCategoryTypeByQuestType`, the category predicates, and the separate main-list methods are in the local inventory's **Available/not allowed** section, so Wayfinder must not call them until the server allows them.

For a useful in-game comparison, first use **Settings → Clear list filters** so completed rows are shown, search is empty, pinned-only is off, and sections are expanded. Turn **Quest IDs** on. Each Wayfinder quest row then starts with `[slot N | type N]`: the one-based active-list slot and the value returned by `GetActiveQuestType(slot)`. The stock journal screenshot does not show a numeric quest ID, so compare exact title and objective text first. Clicking a row also checks whether Wayfinder can resolve that returned type back to an active-list slot before asking the client to track it; this establishes internal consistency but is not an independent canonical-ID check. Refresh and record the `WF` marker plus `A/T/C/I/U`, `E/R`, `D/P/S`, and the API sample. Compare a small, representative set of native journal rows—at least one main/story, normal/zone, daily, weekly, and vocation quest—by exact title, native category, and `[slot N | type N]` prefix. Repeat with a completed row if one is visible. This reveals whether a native row appears in the active list and which type it uses; matching titles absent from the active-list scan may belong to the separately enumerated main list. It also separates category/membership mismatch from filters or rendering. Do not infer category from numeric ID ranges, title, or objective count. Exact classification still requires the permissioned methods above or a server-provided journal enumeration API.

Stock `quest_context_common.lua` builds its display from active entries plus a separate main-quest list, then applies `AddableQuest`, which excludes hidden, today, saga, and public quests. The active-list pass does not use `IsCompleted` as a membership test; completion is used elsewhere for status presentation and behavior. Therefore, filtering completed entries can omit entries that the stock journal still displays. Wayfinder now shows completed entries by default. The runtime category filters and separate main-list APIs needed to reproduce stock membership are marked not allowed locally. Wayfinder's offline catalog contains today/saga tags, but does not use them to filter because the catalog is AA 10.8.1.0 and the latest ArcheRage log reports client 10.0.2.9. Hidden/public exclusions and the separate main-quest list are still missing. This does not prove exact parity with the player's journal; the last supplied comparison was 497 API slots versus 57 journal entries.

The installed `choretracker/choretracker.lua` checks whether a quest ID appears in the active list and then requires `IsCompleted(questId) ~= true` for its in-progress feature. Its `RefreshActiveQuests` loop also applies ChoreTracker-specific race and user-mode filters, so its visible rows are not a copy of the native quest journal. It resolves the active-list index before calling `SetTrackingActiveQuest`. Wayfinder follows the verified active-list, completion, and index-lookup patterns where they are relevant.

The local stock implementation at `aagamedump/scriptsbin/x2ui/questcontext/quest_context_common.lua` exposes the exact client-side checks. `GetQuestItemsGroupedByCategory` loops through the active list, then a separate main-quest list, and applies `AddableQuest` to both. `AddableQuest` excludes hidden, today, saga, and public quests. The stock Lua helper `IsExistQuestTypeInJournal(qType)` is not an X2 API: it searches the active list; if `IsMainQuest(qType)` is true, it additionally requires `GetActiveQuestListStatusByType(qType) ~= 0` and `IsCompleted(qType) == false`; otherwise it accepts the active-list ID. This separates quest-list construction from the helper's journal-state check: list construction uses category exclusions and the separate main-quest list, while the helper also applies a main-quest status/completion gate. The directly named X2 predicates `IsProgressQuestInJournal` / `IsReadyQuestInJournal` exist in the dump but are not used by this helper; they remain exploratory candidates, not confirmed replacements. This stock source explains why the 497-slot active list alone may not reproduce the journal and does not authorize calls to restricted methods.

## Smallest API gap for native journal parity

The local `api_functions.txt` and generated `X2Quest.txt` were updated on October 28, 2026, but they still mark the September 8 journal objective count/text and October 27 active-objective text permissions as unavailable. Treat those exact official announcements as newer permission evidence. Other generated-reference signatures remain unavailable unless a server update explicitly enables them.

The server permission set for a parity attempt is the following. The stock `GetQuestItemsGroupedByCategory` loop reads active entries and a separate main-quest list, then passes both through `AddableQuest`; two additional journal-state predicates may offer a more direct membership check. For the smallest exact-membership contract, the server could instead expose an aggregate `GetQuestJournalQuestCount()` / `GetQuestJournalQuestType(index)` pair that enumerates the same quest rows the native journal shows. This proposed pair is not a current API.

- Native category membership: `IsHiddenQuest`, `IsTodayQuest`, `IsSagaQuest`, and `IsPublicQuest`, used by stock `AddableQuest`.
- Main-story membership and grouping: `IsMainQuest`, `GetMainQuestListCount`, and `GetMainQuestType`.
- Direct journal membership/state: `IsProgressQuestInJournal` and `IsReadyQuestInJournal`, for checking whether an active-list candidate is currently in progress or ready in the journal.

The seven category/main-list getters let Wayfinder reproduce the observed stock list filtering and grouping. The two status getters are needed to reproduce the stock helper's main-quest journal-state check. The two journal-state predicates may offer a direct alternative, but stock does not use them and their semantics must be confirmed if enabled. All eleven methods are marked not allowed in the installed inventory. Exact stock row state is a separate increment: `GetActiveQuestListStatus(index)` and `GetActiveQuestListStatusByType(questType)` are used to distinguish inactive/ready states. By-type journal objective counts/text, category labels, icons, and selection state still require their own enabled APIs; the currently enabled objective getters do not establish exact membership or complete every stock row detail.

These remaining methods are candidates for future server enablement, not APIs used by the addon today. ArcheRage's original addon announcement says its `api_functions` inventory lists currently available methods and that additional methods may be added upon player request; see the [official addon announcement](https://na.archerage.to/forums/threads/server-updates-10-29-lua-addons-enabled-and-more.12038/). The current quest-membership checklist items remain pending until an updated allowlist or explicit server announcement confirms access.

## Current diagnostics

The second diagnostic line includes `JC` for active-list entries with a positive result from the server-enabled `GetQuestJournalObjectiveCount(index)`. Wider panels also show `J0` (zero counts) and `J?` (failed or malformed reads); narrow panels show only `JC`. The per-state sample appends `J<count>` or `J?`. Stock `GetQuestObjectives` first resolves a quest ID with `IndexFromQuestType`—a scan of `GetActiveQuestListCount` / `GetActiveQuestType`—then passes that active-list index to `GetQuestJournalObjectiveCount`. Stock code also has a distinct `GetQuestJournalObjectiveCountByType(questType)` helper, but that overload is not enabled for addons. These counts are not used to remove rows and do not prove journal membership. Compare them with the native journal before deciding whether objective count can safely support an optional filter; completed stock rows may have no remaining objectives.

The first on-screen scan counter starts with a short build marker derived from `BUILD_ID` (currently `WF29`). A different marker after refresh indicates an older loaded script. If the marker is missing, check addon startup diagnostics too: initialization may have failed before the tracker label was drawn.

The same line reports coarse function-presence flags without invoking restricted methods: `F` means all four stock `AddableQuest` category predicates are exposed as functions, `J` means both direct journal-state predicates are exposed, `L` means main-quest classification and list methods are exposed, and `S` means both active-list status getters are exposed. A `+` reports function references; it does **not** prove calls are permitted or behavior matches the stock client. A `-` means one or more references in that group are missing. The flags are a diagnostic for future allowlist changes, not a quest filter.

- `T`: unique numeric quest IDs successfully read.
- `C`: IDs reported completed by `IsCompleted`.
- `I`: IDs reported not completed.
- `U`: completion-state errors or non-boolean results.

- `H`: title getter fallbacks; a visible row uses `Quest <id>` when title lookup fails.
- `M`: invalid ID values.
- `Q`: duplicate IDs skipped.
- `X`: active-list slot reads that raised an error.
- `O`: active-objective getter calls that raised an error or returned an unexpected type. This is expected to remain zero when objective display is off.
- `V+` / `V-`: objective rows are shown / hidden.
- `D+` / `D-`: completed entries are included / hidden.
- `P+` / `P-`: pinned-only filtering is enabled / disabled.

For example, `A497 T497 C440 I57 U0` indicates 57 IDs are marked not completed by the allowed completion API. It does not establish that those 57 exactly match the visible native journal: stock membership does not simply filter by completion. `U497` means completion state could not be read, and Wayfinder keeps those entries visible pending a live check. The separate debug summary reports catalog matches (`K`) and saga/today tags (`F`). Compare `E` and `R` with the native quest-log count after a fresh in-game refresh. If `E0` appears while the native journal contains quests, the completion predicate is incompatible with the current client's active-list values and must not be treated as a journal filter.

If a refresh renders no quest rows, Wayfinder also prints up to three sample active-list IDs, titles, and completion results (`C`, `I`, or `?`) to the addon debug output. It suppresses the sample when the same empty-scan result repeats. It tries `aaprint` first, then falls back to the system chat dispatcher if that logger errors or is unavailable. This helps distinguish a completed-state filter mismatch from bad title data or rendering failure without calling restricted APIs. The visible empty-state label separately distinguishes a zero-slot API result from nonzero slots with no valid IDs, and starts with the current build marker so a stale Addon Manager refresh is apparent in the same line. When objective display is enabled, `O` counts objective getter failures and `V+` confirms the setting; when disabled, `V-` appears and Wayfinder does not call that getter.

Title search updates the scan as the search text changes; clearing the edit box restores candidates immediately. The tracker status labels nonempty totals as API quest candidates or filtered candidates, never as a confirmed native journal count. If sections are collapsed, it reports visible rows separately from candidates remaining after filters. Empty-state messages point to the relevant settings when completed-only or pinned-only filters hide every row. This distinguishes user filters from an unavailable or malformed quest API.

The tracker shows an API sample on every scan (`API slot@ID: slot@id:state=title`), including when rows render. It prefers a not-completed (`I`) sample, then a completed (`C`) sample, then an unknown (`?`) state. Here `I` means only that `IsCompleted` returned `false`; it does not prove native journal membership or tracking status. The slot number points back to the exact `GetActiveQuestType(index)` position. If no valid IDs were read, the first malformed slot is shown instead. This keeps troubleshooting evidence visible even when addon debug output is not visible in chat. It does not change quest filtering.

Objective display is opt-in and persisted with profiles. When enabled, Wayfinder queries `GetActiveQuestObjectiveText(questType, index)` for rendered quest rows, beginning at index 1 and stopping on `false` or `nil`, up to the `MAX_QUEST_OBJECTIVE` limit. Read errors and unexpected result types increment `O` in the filter diagnostic line; `V+` / `V-` shows the toggle state. Objective rows are intentionally inert to mouse clicks and are excluded from rendered-quest counts. This getter is explicitly enabled by the October 27, 2026 server update, despite the older local inventory marking it unavailable; live API access and text layout remain unverified.

Portable profile format `WAYFINDER_PROFILE_V1` remains backward-compatible when optional completion-alert or sound fields are absent; these default off. The `showCompletionLabel` field is also optional for older exports and defaults on. The new `keyboardNavigation` field is optional for older exports and defaults off. Other required profile fields remain mandatory.

The scan summary reports active-list read errors, malformed IDs, duplicate IDs, objective getter failures, title-getter fallbacks, eligible title/pin filter results, API quest candidates, and rendered rows. Collapsed sections can make visible rows fewer than candidates; the tracker status reports both counts in that case. Objective rows are excluded from the rendered-row count. Empty-scan samples prefix a fallback title with `?`. The `A` to `T` gap can therefore be separated into failed reads, malformed values, and duplicates instead of being mistaken for quest-completion filtering. Up to three malformed active-list slots are logged as `index:type` samples. Control characters in returned titles are replaced with spaces and surrounding whitespace is trimmed; missing or unusable titles remain visible as `Quest <id>`.

If the active-quest API is missing, its count call fails, or its count is not a finite nonnegative integer, Wayfinder hides all prior quest rows, resets the scroll position and content height, and changes counters to `?`. It does not leave a previous successful scan on screen as if it were current data. The opt-in accept-and-auto-track path applies the same count validation before iterating the list.

## Offline quest catalog

`quest_catalog.lua` is generated from the local `aagamedump/db/195-english.part_aa` and `part_ab` SQLite data. The source database identifies itself as AA 10.8.1.0 English (2024-05-02); the latest ArcheRage log reports client 10.0.2.9. The catalog stores context ID, English title, zone label, continent label, saga membership, and today-quest membership. The generator maps `w_` zone-group IDs to Nuia, `e_` to Haranya, and `o_` to Auroria. Representative entries were cross-checked with ArcheRage's wiki: [`Two Crowns`](https://wiki.archerage.to/na-en/db/quests/2472) belongs to Nuia, [`Ynystere`](https://wiki.archerage.to/na-en/db/quests/2311) belongs to Haranya, and [`Exeloch`](https://wiki.archerage.to/na-en/db/quests/5436) is on Auroria. Sea, instance, test, and other special prefixes remain `Other`. The generator normalizes title whitespace/control characters to match runtime title cleanup, omits explicit `DO NOT TRANSLATE` title placeholders, and uses `Unknown Zone` when no zone label exists; it does not substitute a quest category as geography. It validates positive unique IDs and complete metadata, then writes to a temporary file and atomically replaces the catalog. Wayfinder accepts metadata only when runtime quest ID and title match exactly; a mismatch falls back to unknown geography and is not filtered. Saga/today tags remain diagnostic until their compatibility is checked in-game. The generator is `tools/generate_quest_catalog.py` and requires the `aagamedump` SQLite parts. This provides offline metadata without calling forbidden APIs, but server-version and localization matches still need live verification.

## Geography and navigation

Quest category and acceptance-zone getters are marked not allowed in the local inventory. Wayfinder now uses the title-checked offline catalog for zone/continent grouping and falls back to `Other / Unknown Zone` when a quest is missing or mismatched. The stock notifier calls `X2Quest:GetQuestDirInfo(questType)` and reads `dist`, `angle`, and `height` to drive per-quest distance text and direction arrows; it refreshes this data during notifier updates. `GetQuestDirInfo` appears in the local inventory's available/not allowed section, so the stock usage does not authorize addon usage. WF29 probes only whether the method is present and does not call it. If ArcheRage enables this getter for addons, it could support sorting candidates that return valid distance info, but it would not identify which candidates are checked in the native tracker; entries without direction data would also need a fallback order. The stock decal APIs remain restricted and must not be called unless explicitly enabled.

## Native quest UI controls

The X2 Addon API defines `UIC_QUEST_LIST` and `UIC_QUEST_NOTIFIER` and documents `ADDON:ShowContent(category, visible)`. Wayfinder's opt-in native visibility settings use these categories and default to side-by-side mode. Startup applies opt-in hides without an unsolicited show call that could open the stock quest log. ## Tracker window bounds

The local UI-bounds definition documents `Uibounds:CorrectOffsetByScreen()` as returning an on-screen offset limited by the screen size and effective widget dimensions. Installed Addon Manager and other addons use this method, then divide by `UIParent:GetUIScale()` before re-anchoring to `UIParent`. Wayfinder applies the same correction after styling/resizing and after dragging, and saves a corrected position when screen bounds require a move. Resolution and UI-scale behavior still needs in-game verification.

Tracker resizing uses eight transparent edge/corner target widgets and the documented `Widget:StartSizing(anchorPoint)` method. The earlier position-based handler called `X2Input:GetMousePos()`, which the local inventory marks “Available/not allowed”; when unavailable it fell back to moving the whole window. WF25 removes that call. Each handle invokes `StartSizing` with its fixed edge or corner anchor, while the tracker interior uses `StartMoving`. Resize and lock behavior still need live-client verification.

WF26 adds optional keyboard navigation using documented widget focus and key handlers. With the option on, clicking a quest selects/focuses it without sending a tracking request; Up/Down move a persistent cursor by quest ID through visible quest rows, and Enter requests tracking through the same current-index lookup used by the track action. ## Events

Wayfinder uses events present in the local ArcheAge definitions and stock UI: `LEFT_LOADING`, `ENTERED_WORLD`, `UI_RELOADED`, `QUEST_CONTEXT_UPDATED`, `QUEST_NOTIFIER_START`, and `ENTERED_SUBZONE`. The proposed names `LOADING_END`, `QUEST_ACCEPTED`, `QUEST_TRACK_CHANGED`, and `ZONE_CHANGED` were not found locally. Stock `quest_context.lua` handles `QUEST_CONTEXT_UPDATED(qType, status)` for `dropped`, `started`, `updated`, and `completed`. However, the local X2 `QUEST_STATUS` type alias lists only `dropped`, `started`, and `updated`; `completed` is confirmed by stock-handler code, not that type alias. Wayfinder offers opt-in auto-track for `started`, using the permitted active list and tracking API, and an opt-in completion chat alert for `completed` through the imported chat API. Event timing and tracking selection still need in-game confirmation.

`QUEST_CONTEXT_UPDATED` is a change notification with one quest ID and a status, not an initial journal snapshot. A cache built from it would omit quests accepted before Wayfinder loaded or while it was disabled, and would become stale if any update were missed. It therefore cannot replace the unavailable startup membership/list APIs and is not used as a quest filter or source of truth. The stock handler rebuilds journal data by querying the restricted category and main-list methods after receiving the event.

The stock quest-context handler treats `QUEST_CONTEXT_OBJECTIVE_EVENT` and `QUEST_CONTEXT_CONDITION_EVENT` as notification events: it displays objective or condition messages, but does not use them to rebuild the quest journal. Wayfinder currently refreshes from `QUEST_CONTEXT_UPDATED` instead of rescanning the full 497-slot candidate list for every notification. Verify in-game that objective progress produces an `updated` status and refreshes the visible objective text; add an additional event hook only if live evidence shows the stock update event is insufficient.
